The project in five minutes

Maa Collection is a phone-first web app for an Indian clothing shop. A salesman scans a tag, types the price the customer agreed to, and records the sale. The owner adds stock, prints tags, approves sales and reads reports.

What we deliberately don't use — and what does the job instead

Redux, Zustand, MobXThe database is the shared state; Server Components read it per request. Small client state stays in components (chapter 9).
React Query, SWR, useEffect + fetchServer Components fetch on the server; after a change we refresh with revalidatePath / router.refresh().

Why so little? Every package is code we must understand, update and ship to cheap phones on shop Wi-Fi. The rule in CLAUDE.md is: no new dependency until a task needs it. Some are planned for later phases, for example IndexedDB (Dexie) for offline selling.

The house rules a front-end developer must know

  • Money is whole paise (129900 = ₹1,299.00). Convert only for display with formatPaise, and read input with rupeesToPaise.
  • The server is the authority. The browser may check things for speed, but the server checks them again.
  • Salesmen never receive purchase prices. Not even hidden in a prop (chapter 4).
  • Every visible text exists in English and Hindi (chapter 13).
  • Use brand-* colours, never fixed hues. The owner can switch among six themes (chapter 10).

Chapter 3

How pages are rendered

If you have built a Vite or Create React App project, the browser built every page. Here the server does most of the work, and Next.js 16 goes one step further: it prepares a ready-made "shell" for each page ahead of time.

Five ways to render, side by side

ModelWhere the HTML comes fromIn our app?
CSR (client-side)An empty HTML page; JavaScript fetches data and builds the UI in the browserNo. Only small interactive parts run in the browser.
SSR (server-side)The server builds full HTML for every request, then React "hydrates" itYes, for everything that needs the logged-in person or live data
SSG (static)HTML is built once at build timeFor the document frame (head, fonts, theme script)
StreamingThe server sends HTML in pieces; slow parts arrive later inside <Suspense>Yes, on every page
Partial prerendering (Cache Components)A static shell built ahead of time; request-specific parts stream into its <Suspense> holesYes: cacheComponents: true in next.config.ts

The rule Cache Components gives us

With cacheComponents: true, Next.js prerenders each route's static shell: everything that does not depend on the request. Anything that reads the request — cookies(), searchParams, params, or connection() — must sit inside a <Suspense> boundary. Its fallback goes into the shell, and the real content streams in at request time. If you forget, the dev overlay shows a "blocking route" warning.

Our two levels of boundaries

src/app/layout.tsx (shortened)<body className="min-h-full flex flex-col">
  <AppearanceSync />
  {/* The person's language (needs the request), so pages render inside this boundary. */}
  <Suspense fallback={null}>
    <LocaleRoot>{children}</LocaleRoot>
  </Suspense>
</body>
  1. The root boundary. Every screen is shown in the person's language, which needs the request: who is logged in, read through a cookie and the database. So LocaleRoot and everything inside it — header, layouts, pages — are rendered per request. Our static shell is therefore small: <html>, the <head> with fonts and the theme script, and <body>. That is right for an app where almost everything depends on the logged-in person.
  2. Page boundaries. Inside that, each page puts its slow, data-heavy part in its own <Suspense>. React can then send the header and the page's frame (with "Loading…") as soon as the language is known, and stream the data in when it's ready, instead of holding the whole screen for the slowest query.

That is why almost every page in the project has the same shape:

src/app/(pos)/pos/page.tsx — complete file (long lines wrapped)import { Suspense } from 'react';
import { loadCounter } from '@/features/pos/load-counter';
import { PosScreen } from '@/features/pos/pos-screen';
import { lookupProductAction } from '@/server/actions/pos';

async function Counter({ searchParams }: {
  searchParams: Promise<{ code?: string | string[] }>;
}) {
  const [{ me, staff }, { code }] = await Promise.all([loadCounter(), searchParams]);
  // Opened from a tag's QR code (/i/<code>): show that item straight away.
  const scanned = typeof code === 'string' ? code.trim().slice(0, 64) : '';
  const found = scanned ? await lookupProductAction(scanned) : null;
  const initial = scanned
    ? { code: scanned, product: found?.ok ? found.data : null }
    : undefined;
  return <PosScreen me={me} staff={staff} initial={initial} />;
}

export default function PosPage(props: PageProps<'/pos'>) {
  return (
    <Suspense fallback={<p className="text-sm text-zinc-500">Loading…</p>}>
      <Counter
        searchParams={props.searchParams as Promise<{ code?: string | string[] }>}
      />
    </Suspense>
  );
}
  • The default export is not async and awaits nothing. It only places the boundary, so the page frame and "Loading…" go out without waiting for data.
  • The inner async component (Counter) does the request work: who is logged in, the staff list, the ?code= in the URL.
  • searchParams is a Promise (since Next 15). We pass it down unawaited, and the inner component awaits it inside the boundary.
  • Promise.all runs the two awaits in parallel instead of one after the other.

connection(): "this needs a real request"

src/server/request-db.tsimport { connection } from 'next/server';
import { getDb, type Db } from '@/db/client';

/** Database access for pages and layouts. `connection()` marks the render as
 *  request-time first, so Next.js never tries to prerender live shop data. */
export async function requestDb(): Promise<Db> {
  await connection();
  return getDb();
}

A database query doesn't touch cookies or headers, so Next.js could otherwise try to run it at build time and freeze yesterday's stock into the page. await connection() stops prerendering at that point. Pages and layouts always get the database through requestDb(), never getDb() directly.

Partial prefetching

partialPrefetching: true makes a <Link> prefetch only the target route's app shell (its static and cached part), once per route, instead of the whole page for every link. In our app most of each screen depends on the logged-in person, so the shell is small and the rest streams in after the tap. That keeps prefetching cheap on phone data. A link can ask for more with prefetch={true}; we don't need that today.

One request, start to finish

1. proxy.tsno valid session cookie? → redirect to /login
2. static shell<html>, head (fonts, theme script), body: sent at once
3. streamed partslanguage known → header and page frame; then each page's data part in its own Suspense
4. hydrationReact in the browser attaches to the Client Components only
5. interactiontaps change local state; saving calls a Server Action
6. refreshthe action's result updates the screen, or the server re-renders the page

Notice that Server Components sit inside I18nProvider, a Client Component. This is allowed because they are passed in as children: the server renders them first and hands the result to the client component to place. A client component cannot import a server component, but it can receive one as children.

What may cross the line

  • Props from server to client must be serialisable: strings, numbers, booleans, plain objects and arrays, Dates, Promises, and JSX (already rendered by the server).
  • Functions cannot cross, with one exception: Server Actions. A client component may import recordSaleAction and call it, and the call becomes a network request (chapter 6).
Props are public Everything a Server Component passes to a Client Component is sent to the browser, even a field you never render. Anyone can read it in DevTools. That is why the counter receives a CounterProduct, a copy of the item made on the server without the purchase price: 
src/server/services/products.ts (shortened)export function toCounterProduct(p: Product): CounterProduct {
  return {
    id: p.id, sku: p.sku, barcode: p.barcode, name: p.name, brand: p.brand,
    category: p.category, size: p.size, color: p.color,
    mrpPaise: p.mrpPaise, pricePaise: p.pricePaise, stock: p.stock,
    // no costPaise, no supplier: a salesman's phone never receives them

}

Composition: keeping data on the server

The All tags page lets the owner switch between Grid and Rows. That switch needs state and localStorage, so it must be a Client Component. But the tags carry prices (including a secret price code), and we don't want them in the browser as data. The solution is to let the client component own only the switch, and give it the tags as server-rendered children:

src/app/(admin)/admin/labels/page.tsx (server, shortened)<TagViews labels={{ view: t('stk.lib.view'), grid: t('stk.lib.view.grid'), … }} summary={…}>
  {grouped.map((g) => (
    <section key={g.key}> … <ul className="tag-row">{g.shown.map(tagCell)}</ul> </section>
  ))}
</TagViews>
src/features/tag-library/tag-views.tsx (client, shortened)'use client';
export function TagViews({ labels, summary, children }: { …; children: ReactNode }) {
  const view = useSyncExternalStore(subscribe, readView, () => 'grid' as const);
  return <div data-view={view}> {/* buttons to switch */} {children} </div>;
}

The browser receives finished HTML for the tags and a tiny component for the switch. The comment in tag-views.tsx says it directly: "The tags themselves are drawn on the server and passed in as children, so nothing about them is sent to the phone as data."

Rule of thumb for new code Start every component as a Server Component. Add 'use client' only to the smallest piece that needs state, effects, event handlers or browser APIs, and push it as far down the tree as you can.

proxy.ts: an optimistic gate

src/proxy.tsexport function proxy(request: NextRequest) {
  const session = verifySession(request.cookies.get(SESSION_COOKIE)?.value, sessionSecret());
  if (!session) return NextResponse.redirect(new URL('/login', request.url));
  // Salesmen may hold catalog/stock/price rights, so /admin pages check permissions themselves.
  return NextResponse.next();
}
export const config = { matcher: ['/pos/:path*', '/admin/:path*'] };

The proxy only checks that the cookie's signature is valid. It does not hit the database, so it stays fast. The real checks — is this person still active, are they the owner, do they have the right — happen in every page and every action (chapter 12).

Async params and typed routes

src/app/i/[code]/route.ts — a tag's QR code opens thisexport async function GET(request: NextRequest, context: RouteContext<'/i/[code]'>) {
  const { code } = await context.params;            // params is a Promise in Next 15+
  const me = await getCurrentStaff();
  if (!me) return NextResponse.redirect(new URL('/login', request.url));
  const product = await findProductByCode(await requestDb(), STORE_ID, decodeURIComponent(code).slice(0, 64));
  const target = product && canAny(me, ['catalog', 'prices', 'stock'])
    ? `/admin/products/${product.id}`
    : `/pos?code=${encodeURIComponent(product?.barcode ?? code)}`;
  return NextResponse.redirect(new URL(target, request.url));
}

RouteContext<'/i/[code]'> and PageProps<'/pos'> are generated from the real folder names, so a typo in a route string is a type error. The same QR code takes the owner to the product page and a salesman to the Sell screen with the item loaded.

React cache(): one query per request

src/server/auth.ts (shortened)import { cache } from 'react';

export const getCurrentStaff = cache(async function getCurrentStaff() {
  const db = await requestDb();
  const session = verifySession((await cookies()).get(SESSION_COOKIE)?.value, sessionSecret());
  if (!session) return null;
  const [person] = await db.select({ … }).from(staff).where(…).limit(1);

The header, the page, getLocale() and several checks all call getCurrentStaff() during one request. cache() remembers the result for that request only, so the database is asked once. The next request starts fresh. It's like useMemo for the server, scoped to one page render.

next/form and the key trick

src/features/tag-library/filter-form.tsx (shortened)export function TagFilterForm({ label, children }: { label: string; children: ReactNode }) {
  const onChange = (event: FormEvent<HTMLFormElement>) => {
    const target = event.target as HTMLInputElement | HTMLSelectElement;
    if (target instanceof HTMLSelectElement || (target instanceof HTMLInputElement && target.type === 'checkbox')) {
      event.currentTarget.requestSubmit();          // picking a filter applies it at once
    }
  };
  return <Form action="/admin/labels" scroll={false} role="search" aria-label={label} onChange={onChange}>{children}</Form>;
}

A GET form puts the filters in the URL (/admin/labels?supplier=…&stock=1), and the server renders the filtered page. The page renders it as <TagFilterForm key={tagLibraryHref(p)}>. When the URL changes, the key changes and React re-creates the form, so its uncontrolled inputs show the new values instead of stale ones.

Server Actions: our API layer

Anatomy of an action

src/server/actions/pos.ts (shortened)'use server';

export type ActionResult<T> = { ok: true; data: T } | { ok: false; error: string };

const saleSchema = z.object({
  operationId: z.string().min(8).max(100),
  productId: z.uuid().optional(),
  quantity: z.number().int(),
  unitPricePaise: z.number().int(),
  soldBy: z.uuid(),
});

export async function recordSaleAction(input: z.input<typeof saleSchema>) {
  const current = await requireStaff();              // 1. who is calling? (again!)
  return run(async () => {
    const data = saleSchema.parse(input);            // 2. never trust the input
    const db = await getDb();
    const result = await recordSale(db, STORE_ID, { ...data, recordedBy: current.id }); // 3. rules
    return { stockLeft: result.stockLeft, totalPaise: result.sale.totalPaise, … };      // 4. plain data
  });
}
  1. Check the person in every action. An action is a public HTTP endpoint: anyone can POST to it, whatever the UI shows.
  2. Validate with Zod. TypeScript types disappear at runtime, and a modified request can send anything.
  3. Call a service. The rules (price ≤ MRP, enough stock, one sale per operationId) live there, inside a database transaction.
  4. Return a result object, don't throw. ActionResult is a union the screen can switch on; error text arrives already translated (chapter 13).

After a change: getting fresh data on screen

  • revalidatePath() in the action tells Next.js that server-rendered data under a path is stale. Approvals call revalidatePath('/', 'layout') because a decision changes totals on Home, Reports, Sales team and My sales.
  • router.refresh() on the client asks the server to re-render the current page and merges the result in place. Scroll position and client state are kept; there is no full reload. The approvals screen and the language switch do this.
  • Return the new values when only this screen needs them. The Sell screen just shows stockLeft from the result.
Why operationId is made on the phone When an item is scanned, the Sell screen stores crypto.randomUUID() with it. If the network drops after the server saved the sale and the salesman taps Record sale again, the same id goes up. The database's unique key spots the repeat and the service returns the first sale. If the id were made inside the action, every retry would get a new id and the item would be sold twice. (The database side is in Lesson 6 of the SQL guide.)

Chapter 8

Closures at work

A closure is a function together with the variables that were in scope where it was created. The function keeps those variables alive for as long as the function itself lives. In React this matters all the time, because each render is a function call with its own props and state.

8.1 Private state: the hardware scanner buffer

USB and Bluetooth barcode scanners act like keyboards: they "type" the code very fast and press Enter. We must tell such a burst apart from a person typing slowly.

src/features/scanning/scanner-keystrokes.tsexport function createScanBuffer(maxGapMs = 100, minLength = 3) {
  let buffer = '';                                  // private: only push() can see these two
  let lastAt = Number.NEGATIVE_INFINITY;
  return {
    push(key: string, at: number): string | null {
      const continues = at - lastAt <= maxGapMs;   // keys close together = one scanner burst
      lastAt = at;
      if (key === 'Enter') {
        const code = continues ? buffer : '';
        buffer = '';
        return code.length >= minLength ? code : null;
      }
      if (key.length === 1) buffer = continues ? buffer + key : key;
      return null;                                  // Shift, Tab, etc.
    },
  };
}

buffer, lastAt, maxGapMs and minLength live on inside the closure between key presses, and nothing outside can change them. No class, no global, no React state (which would re-render on every key). Each call to createScanBuffer() gets its own fresh pair. The test file creates a new one per test, so tests never share state.

src/lib/i18n/index.tsexport function makeT(messages: Messages): T {
  return (key, vars) => fill(messages[key] ?? en[key] ?? key, vars);
}

8.6 The stale-closure trap, and the "latest ref" fix

A key listener attached once with [] dependencies closes over the first render's values forever. Here is how the hardware scanner hook would look if written naively:

✗ Buggy version (not in our code)export function useScannerKeystrokes(onScan: (code: string) => void, enabled = true) {
  useEffect(() => {
    if (!enabled) return;
    const buffer = createScanBuffer();
    const handleKeyDown = (e: KeyboardEvent) => {
      const code = buffer.push(e.key, e.timeStamp);
      if (code !== null) onScan(code);       // ← the onScan of the render that ran this effect
    };
    window.addEventListener('keydown', handleKeyDown);
    return () => window.removeEventListener('keydown', handleKeyDown);
  }, [enabled]);                    // onScan left out, so the buffer isn't reset
}

What goes wrong: onScan is the Sell screen's handleScan, which uses t for its messages. Switch the language to Hindi and the screen re-renders, but the listener still calls the old handleScan, so "not found" appears in English. Adding onScan to the dependencies "fixes" that but re-attaches the listener and throws away the half-typed buffer on every render.

✓ What the project does — src/features/scanning/scanner-keystrokes.tsexport function useScannerKeystrokes(onScan: (code: string) => void, enabled = true) {
  const onScanRef = useRef(onScan);
  useEffect(() => { onScanRef.current = onScan; });   // after every render: keep the newest

  useEffect(() => {
    if (!enabled) return;
    const buffer = createScanBuffer();
    function handleKeyDown(event: KeyboardEvent) {
      if (event.ctrlKey || event.metaKey || event.altKey) return;
      if (isTextEntry(event.target)) return;
      const code = buffer.push(event.key, event.timeStamp);
      if (code !== null) {
        event.preventDefault();
        onScanRef.current(code);           // read at call time: always the newest
      }
    }
    window.addEventListener('keydown', handleKeyDown);
    return () => window.removeEventListener('keydown', handleKeyDown);
  }, [enabled]);
}

The listener is attached once (the buffer survives), but it reads onScanRef.current when a scan happens, which is always the newest function. The camera scanner uses the same trick for onDecode and onClose. React 19.2+ also offers useEffectEvent for exactly this job. The ref pattern does the same and is what you'll find in our code.

When would we add a client store?

When state is (a) owned by the phone, (b) needed by distant components, and (c) changing often. The planned case is offline selling (backlog phase 6): sales recorded with no network must be queued on the phone (IndexedDB via Dexie), shown as "waiting to sync", and sent when the network returns. If you join that work, a small store (or useSyncExternalStore around the queue) is the right tool; Redux's extra structure would be heavier than we need.

Question to ask before adding global state "Could this live in the database, the URL, or one component?" In this project the answer has been yes every time so far.

Chapter 17

Answers

1 · The staff list

(pos)/pos/page.tsx → Counter awaits loadCounter() (features/pos/load-counter.ts), which calls requireStaff() and listStaff(await requestDb(), STORE_ID, { activeOnly: true }). It keeps only { id, name } and passes staff as a prop to PosScreen, which hands it to StaffSelect. Nothing is fetched from the browser; the list arrives inside the streamed page. Only id and name cross the boundary, not roles, PIN hashes or rights.

2 · Server vs client

PosPage must be server: it reads the session cookie and the database (impossible in the browser, and the DB credentials must never ship), and it uses searchParams to pre-load a QR-scanned item before any JavaScript runs. PosScreen must be client: it holds state that changes with every tap (useState, useTransition), and it uses browser APIs through its children: the camera, Web Audio sounds, vibration, keyboard listeners.

3 · Why pages check again

The proxy checks only that the cookie is validly signed. Example: the owner removes Pradeep's stock right, or deactivates him, while his phone is still logged in. His cookie is still valid, so the proxy lets /admin/stock/receive through. Only requirePermission('stock'), which re-reads him from the database through getCurrentStaff(), sends him back to /pos. (The action behind that page checks again for the same reason.)

4 · Where operationId comes from

It identifies one intended sale. Made when the item is shown, it stays the same for every retry of that sale, so the database's unique key turns a double tap or a retry after a timeout into "return the first sale". If the action made it, every retry would carry a fresh id, and a sale whose first response was lost would be recorded twice and take stock twice. A new scan gets a new id, so the next customer's sale is never confused with this one.

5 · Without useCallback

onClose would be a new function on each PosScreen render. DoneOverlay's effect depends on it, so after each re-render React would clear the old timer and listener and start a fresh 1.6-second timer. Anything that re-renders PosScreen while the card is open pushes the auto-close back. It still closes eventually (or on a tap), but timing becomes unpredictable and the key listener is re-added each time.

6 · Stale closure

With [enabled] as the dependency, the listener keeps the onScan from the render that attached it. That is ScanInput's submit, which calls the handleScan of that time, holding the English t. After switching to Hindi, the "not found" message still appears in English, until something toggles enabled (for example opening the sell form) and the effect re-runs. Adding onScan to the dependencies "fixes" the language but re-attaches the listener and drops the buffer on every render. That is why the ref exists.

7 · useState(readView())

Server: readView's try/catch saves it — localStorage is undefined, the access throws, and it returns 'grid'. Without that try, the server render would crash. Phone with Rows saved: the server HTML says grid but the first client render says rows, so React reports a hydration mismatch and patches the UI, with a visible jump. Other components on the page wouldn't update when the view changes either, because nothing subscribes to the store. useSyncExternalStore with a server snapshot solves all three.

8 · Removing the page's Suspense

A component that is still waiting hands control to the nearest <Suspense> above it. Without the page's own boundary, that is the root layout's <Suspense fallback={null}> around LocaleRoot. Everything inside it — the header, the bottom tabs, the whole Sell frame — waits for Counter's data, and until then Vishal sees a blank page (the fallback is null). With the page boundary, the header and "Loading…" appear as soon as the language is known and only the counter area waits. Nothing breaks, but the screen feels slower. That is why every page keeps its data part in its own boundary.

9 · FirstTimeTip

One clean versionconst listeners = new Set<() => void>();
function subscribe(listener: () => void) {          // module scope: created once
  listeners.add(listener);
  return () => { listeners.delete(listener); };
}
export function FirstTimeTip({ id, text, helpHref }: { … }) {
  const dismissed = useSyncExternalStore(subscribe, () => isDismissed(id), () => true);
  …
}

The snapshot still closes over id. Run pnpm test and the tip-related e2e tests afterwards.

10 · "Big text" plan

Where: it's a per-phone preference (one phone may have weaker eyesight behind it), so localStorage + useSyncExternalStore, like sound. It isn't shop data (no database), nor page state (no URL). Files: a small store module (read/save/subscribe) in src/features/appearance/ or feedback/; a switch on the Settings screen (a client component inside (admin)/admin/settings/page.tsx, or the header menu if salesmen need it); pos/product-card.tsx reads it and picks a bigger class. Strings go in src/lib/i18n/modules/… in both English and Hindi. Add a unit test for the store, and update the Guide story if the screen changes (features/guide/stories.ts). Better still, a data-text="big" attribute on <html> set by the head script, plus a CSS rule, gives no flash at all, like the theme.

Chapter 20

Glossary

App Router
Next.js routing by folders in src/app, with layouts and React Server Components.
App shell / static shell
The part of a page that is the same for every request; prerendered and prefetched.
Cache Components
Next 16 mode (cacheComponents: true): static shell plus streamed request-time parts inside Suspense.
Client Component
A component in a 'use client' file; rendered to HTML on the server, then hydrated and interactive in the browser.
Closure
A function plus the variables in scope where it was created, kept alive with it.
connection()
Tells Next.js the rest of the render needs a real request; used in requestDb().
DTO
"Data transfer object": a copy of data shaped for its receiver, e.g. CounterProduct without cost.
Hydration
React in the browser attaching event handlers and state to server-rendered HTML.
Hydration mismatch
The first browser render differs from the server HTML; React warns and patches.
Idempotent
Doing it twice has the same effect as once; our sales are, thanks to operationId.
Partial prefetching
<Link> prefetches the target's app shell so navigation paints instantly.
Portal
Rendering a component's output into another DOM node (here document.body) while keeping it in the React tree.
Proxy (proxy.ts)
Code that runs before matching routes; Next 16's new name for middleware.
PWA
Progressive Web App: a website installable to the home screen; ours via manifest.ts.
RSC payload
The serialised result of Server Components (and the props to Client Components) sent to the browser.
Route group
A folder in brackets, such as (pos); groups routes without changing the URL.
Route handler
A route.ts exporting GET/POST functions: plain HTTP, no page.
Server Action
An async function in a 'use server' file that the client can call; a public endpoint underneath.
Server Component
The default component type in the App Router; runs only on the server and can be async.
Stale closure
A long-lived callback still holding values from an old render.
Streaming
Sending HTML in pieces; Suspense fallbacks are replaced as their content is ready.
Suspense
A boundary with a fallback shown while the content inside is still loading.
Transition
A state update React treats as non-urgent; with async functions it gives a pending flag for Server Action calls.
useSyncExternalStore
A hook to read a store outside React (here localStorage) safely, with a separate server value.
