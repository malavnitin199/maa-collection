Chapter 1

The big picture

Before any SQL: what a database is, where ours lives, and what happens inside it when a salesman sells a kurta.

A database is a set of very strict registers

Think of the shop's old paper registers: one book for items, one for sales, one for staff. A relational database is the same idea, but strict and fast:

  • Each register is a table (for example products).
  • Each line in the register is a row (one item: "Anarkali Kurta, M, Blue").
  • Each column heading is a column (name, size, stock…), and every row must fit it: a number column only takes numbers.
  • Rows point to rows in other tables with an id (a sale says which product and which salesman, by their ids). That is the "relational" part.

SQL (Structured Query Language, said "S-Q-L" or "sequel") is the language you use to ask the database questions and to change what is in it. It reads almost like English:

Our first querySELECT name, size, color, stock
FROM products
WHERE stock <= 2;

"Show me name, size, colour and stock from the products table, but only the items with 2 or fewer pieces." That is the low stock list on the owner's Home screen.

Which database do we use?

We use PostgreSQL (often called "Postgres"): free, very reliable, used by banks and big shops. It runs in three places:

WhereWhat it isUsed for
Neon (in Singapore)Postgres in the cloud, connected to VercelThe live shop — real items and sales
PGlite on your laptopA full Postgres engine that runs inside the app, saved in the folder .pglitepnpm dev — trying the app locally with demo data
PGlite in memoryThe same engine, kept only in memoryAutomatic tests — a fresh, empty shop for every test

It is the same SQL everywhere. What you learn on your practice database works on the live shop.

The switch lives in src/db/client.ts: if the setting DATABASE_URL starts with postgres:// the app talks to that server (Neon); otherwise it starts PGlite.

The house rules (used in every table)

RuleWhy
Money is whole paise (integer): ₹1,299.00 is stored as 129900Decimal numbers in computers can round wrongly (0.1 + 0.2 ≠ 0.3). Whole paise never do. Columns end in _paise.
Every row has an id (a uuid like 1f96477a-…)Names change; ids never do. Other tables point to the id.

Sales and stock history are never edited or deleted ("append-only")A mistake is fixed by adding a new correcting row, so the history always adds up (Lesson 6).
Sales keep a copy of the name, size, MRP and purchase price at that moment ("snapshots")If the price changes tomorrow, yesterday's sale and profit stay true.
Times are stored with a time zone (timestamp with time zone)"Today" is counted in India time, not the server's time (Lesson 3).
Chapter 4 · Lesson 1

Reading data: SELECT

Ninety per cent of SQL is asking questions. Every question has the same shape.

The shape of every questionSELECT  columns you want
FROM    the table
WHERE   which rows        -- optional
ORDER BY how to sort      -- optional
LIMIT   how many          -- optional

Example: kurtis in stock

QuerySELECT sku, name, size, color, stock
FROM products
WHERE category = 'Kurti' AND stock > 0
ORDER BY name
LIMIT 5;
skunamesizecolorstock
MAA-KR-002Demo Chikan KurtiLWhite3
MAA-KR-001Demo Printed KurtiMBlue5
MAA-KR-003Demo Rayon KurtiXLGreen4
MAA-KR-004Demo Straight KurtiMPink5

Real result from the practice copy with the demo data.

  • Text goes in single quotes: 'Kurti'. Numbers don't: 0.
  • AND means both must be true; OR means either.
  • Comparisons: = <> (not equal) > < >= <=.
  • ORDER BY name sorts A–Z; add DESC for Z–A.
  • SQL words can be any case (select = SELECT). We write them in capitals so they stand out.
  • End each statement with ;.

Searching: LIKE and ILIKE

The Products search box finds "kurta" inside any name, in any case. In SQL that is ILIKE with % meaning "anything here":

QuerySELECT sku, name, size
FROM products
WHERE name ILIKE '%kurta%';    -- I = ignore case; LIKE would be case-sensitive

In the project this lives in listProducts (products.ts), which searches name, SKU, brand, category and colour at once, joined with OR.

Empty values: NULL

Some columns may be empty. In SQL "empty" is NULL ("we don't know"), and it is special: you can't compare it with =.

QuerySELECT name, size FROM products WHERE cost_paise IS NULL;      -- no purchase price entered
SELECT name, size FROM products WHERE supplier_id IS NOT NULL;  -- has a company

The owner's Needs attention screen asks exactly these questions: items without a photo, a company, or a purchase price.

Doing maths in a query

QuerySELECT name, mrp_paise / 100.0 AS mrp_rupees,
       (mrp_paise - price_paise) / 100.0 AS discount_rupees
FROM products;

AS gives a result column a new name. Dividing by 100.0 (not 100) keeps the paise after the point.

JOIN or LEFT JOIN?

KindKeeps…Use it when
JOIN (inner)only rows that have a match on both sidesevery row must have a partner (every sale has a seller)
LEFT JOINevery row on the left, with empty (NULL) columns when there's no matchthe partner is optional (old stock with no company)

Old stock tagged without a company has supplier_id = NULL. With a plain JOIN those items would vanish from the list; with LEFT JOIN they stay, with company = NULL. That is why the All tags page uses LEFT JOIN.

A real five-table join: the All tags page

listTagLibrary in src/server/services/tag-library.ts needs, for every item: its company, who made the tag, and the delivery it came in. In SQL it is:

What the All tags query does (simplified)SELECT p.*, s.name AS supplier_name, st.name AS created_by_name,
       r.id AS receipt_id, r.bill_number, r.created_at AS receipt_at
FROM products p
LEFT JOIN suppliers s        ON s.id = p.supplier_id
LEFT JOIN staff st           ON st.id = p.created_by
LEFT JOIN stock_movements m  ON m.product_id = p.id AND m.reason = 'opening'
LEFT JOIN stock_receipts r   ON r.id = m.ref_id
WHERE p.store_id = 'maa-collection' AND p.active
ORDER BY p.created_at DESC, p.name;

Each item's first stock movement (reason 'opening') points to the delivery that created it. Following that chain gives the bill number and date the page groups by.

Chapter 6 · Lesson 3

Counting and grouping

Every number on the owner's Home, Reports and Sales team screens is a group-and-count query.

Who sold how much?

Query — sales per salesman, approved sales onlySELECT st.name AS seller,
       COUNT(*)                    AS bills,
       SUM(sa.quantity)            AS pieces,
       SUM(sa.total_paise) / 100.0 AS rupees
FROM sales sa
JOIN staff st ON st.id = sa.sold_by
WHERE EXISTS (SELECT 1 FROM approval_decisions d
              WHERE d.sale_id = sa.id AND d.decision = 'approved')
GROUP BY st.name
ORDER BY rupees DESC;
sellerbillspiecesrupees
Balram131317,300.00
Vishal8814,150.00
Pradeep7710,850.00
Nitin333,310.00

Real result on the demo data — the same numbers the Sales team page shows.

  • GROUP BY st.name makes one result row per salesman.
  • COUNT(*) counts rows in each group; SUM(…) adds them up. Others: AVG, MIN, MAX.
  • EXISTS (…) keeps a sale only if a matching "approved" row exists. Since plan v12, only approved sales count anywhere. In the code this is one shared piece, saleApproved in approvals.ts, added to every report.

Per shop day — and the time zone trap

The database stores times as an exact moment. "Which day was it in the shop?" depends on the time zone: 1:00 am in India is still the previous evening in London.

Query — sales per shop daySELECT (sa.created_at AT TIME ZONE 'Asia/Kolkata')::date AS shop_day,
       COUNT(*) AS bills, SUM(sa.total_paise) / 100.0 AS rupees
FROM sales sa
GROUP BY shop_day
ORDER BY shop_day DESC
LIMIT 7;
shop_daybillsrupees
2026-11-1678,570.00
2026-11-1556,360.00
2026-11-1489,820.00
…
  • AT TIME ZONE 'Asia/Kolkata' turns the moment into Indian clock time.
  • ::date keeps only the date (:: means "convert to").
  • The services start "today" and "this month" with date_trunc('day', now AT TIME ZONE 'Asia/Kolkata') — see periodStarts in reports.ts. A unit test checks that a sale at 00:30 India time counts as today.

HAVING: filter the groups

WHERE filters rows before grouping; HAVING filters groups after. "Categories with more than 10 pieces":

QuerySELECT category, SUM(stock) AS pieces
FROM products
GROUP BY category
HAVING SUM(stock) > 10;

FILTER: count only some rows

Profit can only be counted for items that have a purchase price. reports.ts uses:

From salesReportcoalesce(sum(quantity * (unit_price_paise - cost_paise))
         FILTER (WHERE cost_paise IS NOT NULL), 0)

coalesce(x, 0) means "x, or 0 if x is empty" — so a day with no sales shows ₹0, not a blank.

Chapter 7 · Lesson 4

Changing data

Three statements change data: INSERT (add rows), UPDATE (change rows), DELETE (remove rows). Our app uses the first two — on purpose.

INSERT: add a row

Adding a companyINSERT INTO suppliers (store_id, name, phone)
VALUES ('maa-collection', 'Shree Ganesh Textiles', '98765 43210');

Columns you leave out get their default: id gets a new uuid, active becomes true, created_at becomes now.

UPDATE: change rows

Changing a priceUPDATE products
SET price_paise = 119900
WHERE sku = 'MAA-KU-001';
Never forget WHERE UPDATE products SET price_paise = 119900; without WHERE changes every item in the shop. Write the WHERE first; on your practice database, try it inside BEGIN; … ROLLBACK; (Lesson 6) so you can undo.

The most important line in the project

When a sale is recorded, recordSale takes the pieces off like this:

The guarded update (what Drizzle sends)UPDATE products
SET stock = stock - 2
WHERE id = '…the item…' AND stock >= 2
RETURNING stock;

Read it as: "take 2 off — but only if there are at least 2 — and tell me how many are left". If there aren't enough, no row matches, nothing changes, and the service tells the salesman "Only 1 left in stock". The check and the change happen in one statement, so two phones can never both take the last piece (Lesson 6).

RETURNING sends back the changed row, so the app knows the new stock without asking again.

Why we (almost) never DELETE

Sales, exchanges and stock history are the shop's accounts. If a row could be deleted, the totals could silently change. So:

  • A rejected sale is not deleted. A new approval_decisions row says "rejected", and a new stock_movements row (reason sale_rejected) puts the pieces back.
  • Clear stock does not delete items. It adds one cleared movement per item and sets stock to 0.
  • The one-off "fresh start" on 16 Nov was a careful script with a full backup first, run once on the owner's request. It is not an app feature.

This style is called append-only: you only ever add rows.

INSERT … SELECT and UPDATE … FROM

Migration 0001 had to turn the old free-text categories into real categories rows, then link every item. Two powerful forms:

From drizzle/0001_suppliers_categories_receipts.sql-- Make one category row for each different category name the items use
INSERT INTO "categories" ("store_id", "name", "code")
SELECT DISTINCT p."store_id", p."category",
       upper(substr(regexp_replace(p."category", '[^A-Za-z]', '', 'g') || 'XX', 1, 2))
FROM "products" p
ON CONFLICT DO NOTHING;

-- Point every item at its new category row
UPDATE "products" p SET "category_id" = c."id"
FROM "categories" c
WHERE c."store_id" = p."store_id" AND c."name" = p."category" AND p."category_id" IS NULL;

Designing tables

Tables are created with SQL too. The rules you write here are the database's own guards — they hold even if the app has a bug.

Our products table (from drizzle/0000_init.sql)

CREATE TABLE (shortened)CREATE TABLE "products" (
  "id"          uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL,
  "store_id"    text NOT NULL,
  "sku"         text NOT NULL,
  "barcode"     text NOT NULL,
  "name"        text NOT NULL,
  "size"        text NOT NULL,
  "color"       text NOT NULL,
  "mrp_paise"   integer NOT NULL,
  "price_paise" integer NOT NULL,
  "cost_paise"  integer,                       -- may be empty: purchase price not known
  "stock"       integer DEFAULT 0 NOT NULL,
  "active"      boolean DEFAULT true NOT NULL,

  CONSTRAINT "products_stock_nonnegative" CHECK ("products"."stock" >= 0),

CREATE UNIQUE INDEX "products_store_sku_uq"     ON "products" ("store_id", "sku");
CREATE UNIQUE INDEX "products_store_barcode_uq" ON "products" ("store_id", "barcode");

Indexes: the book's index

An index lets Postgres find rows without reading the whole table — like the index at the back of a book. We add them where we search often: (store_id, barcode) for every scan, stock_movements (product_id, created_at) for an item's history. A UNIQUE index is also a guard (no duplicates).

Migrations: changing tables safely

Real shops can't throw away their data to change a table. So every change is a small numbered SQL file, applied once, in order:

FileWhat changed

Normalisation (the PRD's section 10), and when we break it

"Don't store the same fact twice": the company's name lives in suppliers, items store only supplier_id. If the company is renamed, every item shows the new name at once.

We break this on purpose for history: a sale stores its own copy of the item's name, size, MRP and purchase price. A sale is a record of what happened, and it must not change when today's price does.

Chapter 9 · Lesson 6

Keeping money and stock correct

This is the part that turns "a database" into "a shop you can trust". Five ideas, all used in this project.

1. Transactions: all or nothing

Recording a sale is three changes: stock down, a sale row, a stock-movement row. If the server crashed after the first, stock would be wrong forever. A transaction wraps them: either all happen, or none.

What recordSale does, in plain SQLBEGIN;
  UPDATE products SET stock = stock - 1
   WHERE id = :item AND stock >= 1 RETURNING stock;       -- 1. take the piece
  INSERT INTO sales (…) VALUES (…) RETURNING id;          -- 2. the sale, with snapshots
  INSERT INTO stock_movements (product_id, quantity_change, reason, ref_id)
  VALUES (:item, -1, 'sale', :sale_id);                     -- 3. the history line
COMMIT;      -- or ROLLBACK if anything failed: as if nothing happened

In the code: db.transaction(async (tx) => { … }) in sales.ts. Every query inside uses tx.

2. The last piece: two phones at once

TimePhone A (Vishal)Phone B (Nitin)Stock
10:00:00scans the last kurta (1 in stock)scans the same kurta1
10:00:05UPDATE … WHERE stock >= 1 → 1 row, stock 00
10:00:05same UPDATE waits for A, then finds stock 0 → 0 rows0
result"Sale done ✓""Out of stock"never −1

Postgres makes the second update wait until the first finishes, then re-checks stock >= 1. Exercise 7 shows the second update changing 0 rows. The CHECK (stock >= 0) rule is a second safety net.

3. Locking a row: SELECT … FOR UPDATE

An exchange first reads the original sale ("how many can still be returned?"), then writes. Between the read and the write, someone else could exchange the same sale. So exchanges.ts and approvals.ts read with a lock:

Lock the sale until this transaction endsSELECT * FROM sales WHERE id = :sale FOR UPDATE;

Anyone else who wants that row waits until we COMMIT.

4. Retries must not double-sell: idempotency

On a weak mobile network, the phone may send "Record sale" twice. Every sale carries a random operation_id made on the phone, and the table has a rule:

From the schemaCREATE UNIQUE INDEX "sales_store_operation_uq" ON "sales" ("store_id", "operation_id");

The second copy breaks the UNIQUE rule, so it can't be saved. The service sees that and returns the first sale instead. The salesman sees one sale; the stock went down once.

Owner approvals use a short form of the same idea. One decision per sale is a UNIQUE index on approval_decisions.sale_id, and the insert says:

What Drizzle sends for an approvalINSERT INTO approval_decisions (store_id, sale_id, decision, decided_by)
VALUES ($1, $2, $3, $4)
ON CONFLICT DO NOTHING;      -- a second tap (or a second phone) changes nothing

5. The ledger always adds up

Every change in pieces is a row in stock_movements. So for every item: stock = sum of its movements. We can check it with SQL:

Find items whose stock does not match their historySELECT p.sku, p.stock, SUM(m.quantity_change) AS ledger
FROM products p
JOIN stock_movements m ON m.product_id = p.id
GROUP BY p.id, p.sku, p.stock
HAVING p.stock <> SUM(m.quantity_change);

Real result on the demo data: 0 rows — all 62 demo items match their history.

The ledger by reason (practice copy): pieces in at opening, out by sales, back by the owner's two rejected sales.

From TypeScript to SQL: Drizzle

In the services you will rarely see raw SQL. You will see Drizzle, a library that lets us write SQL as TypeScript. Once you know SQL, Drizzle is easy to read — it uses the same words.

  .where(and(eq(products.id, product.id), gte(products.stock, input.quantity)))
  .returning({ stock: products.stock });

Why $1, $2? (Safety)

Drizzle never pastes your values into the SQL text. It sends them separately as parameters. So if someone types '; DROP TABLE sales; -- into the search box, it is searched as plain text, not run as SQL. This attack is called SQL injection. Always use Drizzle's helpers or the sql`…` template with ${value}. Never glue strings together into SQL.

8 · The guarded update, twiceBEGIN;
UPDATE products SET stock = stock - 2
 WHERE sku = 'MAA-KU-002' AND stock >= 2 RETURNING sku, stock;

 WHERE sku = 'MAA-KU-002' AND stock >= 2 RETURNING sku, stock;
-- (0 rows)           UPDATE 0   (none left: the WHERE no longer matches)

9 · Break the price ruleUPDATE products SET price_paise = mrp_paise + 100 WHERE sku = 'MAA-KU-001';
-- ERROR: new row for relation "products" violates check constraint "products_price_le_mrp"

SELECT p.name, s.name
FROM products p

Chapter 16

Glossary

Append-only
Only ever add rows; fix mistakes with a new correcting row. Our sales and stock history work this way.
Column
One kind of value in a table (name, stock), with a fixed type.
Constraint
A rule the database enforces itself: NOT NULL, CHECK, UNIQUE, FOREIGN KEY, PRIMARY KEY.
Drizzle (ORM)
The library that lets our TypeScript describe tables and build SQL queries.
Foreign key
A column that must point to an existing row in another table (sales.product_id → products.id).
GROUP BY
Turns many rows into one row per group, so you can COUNT or SUM each group.
Idempotent
Doing it twice has the same effect as once. Our sales are, thanks to operation_id.
Index
A lookup structure that finds rows fast without reading the whole table.
JOIN
Combining rows from two tables that match on a condition.
Ledger
The full history of changes (stock_movements). Stock always equals its sum.
Migration
A numbered SQL file that changes the tables, applied once, in order (drizzle/0000…0007).
Neon
The cloud company running the live shop's PostgreSQL.
NULL
"No value / unknown". Compare with IS NULL, never = NULL.
Paise
1/100 of a rupee. We store money as whole paise so it never rounds wrongly.
Parameter ($1)
A value sent separately from the SQL text — protects against SQL injection.
PGlite
PostgreSQL that runs inside the app (local development and tests).
PostgreSQL
The database system we use. "Postgres" for short.
Primary key
The column that uniquely names each row; ours is always id (a uuid).
psql
PostgreSQL's command-line program for typing SQL.
Query
A question to the database (usually a SELECT).
Row
One record in a table: one item, one sale.
Schema
The design of all tables. Ours: src/db/schema/index.ts.
Seed
Starter data put into an empty database (pnpm db:seed).
Snapshot
A copy of a value at a moment (a sale keeps the MRP of that day).
SQL injection
An attack where typed text is run as SQL. Prevented by parameters.
Table
A set of rows with the same columns — one "register".
Transaction
A group of changes that all happen or none do (BEGIN … COMMIT / ROLLBACK).
uuid
A long random id that is unique everywhere.
